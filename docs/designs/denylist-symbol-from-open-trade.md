# Design: Deny a Symbol from an Open Trade

Generated by /office-hours on 2026-09-20
Branch: refactor/remove-sidestep-mode
Repo: TBMoonwalker/moonwalker
Status: APPROVED
Mode: Builder

## Problem Statement

A user watching the open-trades table sees a symbol (e.g. `FO0`) that they no
want Moonwalker to ever trade again. Today the only way to block future entries
is to leave the trade table, open the filter config, hand-type the symbol into
`pair_denylist`, and save. The intent forms on the open trade itself, so the
action should live there. The feature: a row action that adds the symbol to
`pair_denylist` so existing trades run as normal but the symbol is not traded in
the future.

## What Makes This Cool

It collapses a multi-step, navigation-heavy workflow into one click on the row
where the user already made the decision. The denylist machinery already exists
end-to-end; this just wires the "one click that lands on the right list" part.
The satisfying moment is "I looked at FO0, I clicked once, and FO0 never trades
again, while my open FO0 trade finishes its run untouched."

## Constraints

- Single-instance deployment. Config changes propagate via the `Config`
  singleton + Redis pub/sub. No clustering concerns.
- Must not disturb already-open trades. The denylist is an *entry* gate only.
- Reuse existing patterns; do not invent a new config-write mechanism.

## Premises

1. The user wants to stop a symbol from *future* trading, not close an open
   position. Agreed (D2).
2. The action lives in the row's "more …" overflow menu, not as a top-level
   button. Agreed (D1).
3. Denying is one-way from the UI; removal is done by editing the
   `pair_denylist` field in the filter config. Agreed (D3).
4. The action appends to `pair_denylist` plus shows a non-blocking badge; no
   `symbol_list` cleanup. Agreed (D4).
5. Hot-reload of the denylist into a running signal plugin is a prerequisite.
   Verified: satisfied by existing code (`service/signal.py` subscribes to config
   changes and reloads plugins, re-running `_prepare_runtime_settings`).

## What Already Exists (the 80%)

- **Denylist logic is fully wired.** `Filter.is_on_deny_list`
  (`backend/service/filter.py:33`), parsed at `signal_runtime.py:351`, gated in
  all three plugins: `sym_signals.py:222`, `websocket_signal.py:570`,
  `asap.py:358`.
- **Open trades are untouched by the denylist.** The denylist is consulted only
  at entry, never in the DCA/TP/SO/exit path. "Existing trade runs as normal" is
  the status quo, not new behavior.
- **Config-write + hot-reload exists.** `PUT /config/single/{key}`
  (`controller/config.py:563`) persists to `AppConfig` and fires the
  pub/sub notify. `service/signal.py:52` subscribes and reloads plugins via
  `_reload_plugin` (`:222`) / `_drain_plugin_reloads` (`:255`), which re-runs
  `_prepare_runtime_settings` (`sym_signals.py:247`) and refreshes
  `self._pair_denylist`. A denylist appended at runtime takes effect in the
  running plugins without a restart.
- **Row-action pattern exists.** `frontend/src/composables/useOpenTradeActions.ts`
  already has `handleDealSell` → `POST /orders/sell/{symbol}-{currency}` and
  `handleDealStop` → `POST /orders/stop/{symbol}-{currency}` (`orders.py:102`),
  with confirm dialog, success/error messaging, and operation-id idempotency.
- **The "more …" menu exists.** It is the `NDropdown` in
  `frontend/src/composables/useOpenTradeColumns.ts:100-176`
  (`overflowOptions` + `onSelect` key-switch). Adding an entry is a one-line
  option plus one `onSelect` case.
- **Badge rendering exists.** `renderSymbolCell` in
  `useOpenTradeColumns.ts:209` already renders `NTag`/`NTooltip` status tags for
  `automation_paused` and `delisting_warning`. A "denylisted" tag is a clone.
- **Denylist reaches the UI.** `configLoad.ts:375` maps `pair_denylist` into the
  config store; `configSnapshotStore` already exposes the snapshot
  (used by `useTradingPauseStatus.ts`).

## Approaches Considered

### Approach A: Reuse the config-write API (recommended)
  Summary: Add a `handleDealDeny` action (clone `handleDealStop`) that calls
  `PUT /config/single/pair_denylist` with the symbol appended (de-duped), renders
  a menu entry and a row badge.
  Effort: S
  Risk: Low
  Pros: Reuses the existing, validated config-write + hot-reload path; smallest
   diff; the "future-only" and "open trade undisturbed" requirements fall out of
   the denylist being an entry-only gate; hot-reload verified working.
  Cons: Relies on the running plugin reload picking up the change (verified to
   work, but the badge should reflect the *desired* state, not only the
   persisted one).
  Reuses: `useOpenTradeActions.ts`, `useOpenTradeColumns.ts` NDropdown +
   `renderSymbolCell`, `PUT /config/single/{key}`, `configSnapshotStore`.

### Approach B: Dedicated `/orders`-style deny endpoint
  Summary: Add `POST /orders/deny/{symbol}-{currency}` that appends to
  `pair_denylist` server-side, mirroring `/orders/stop`. Frontend action calls
  it.
  Effort: S/M
  Risk: Med
  Pros: Isolates the denylist-mutation semantics in one endpoint; can host the
   de-dup normalization server-side.
  Cons: Duplicates the config-write path that already exists; a symbol
   string-normalization boundary lives in two places (frontend normalize +
   server append) and can drift.
  Reuses: `orders.py` handler shape.

### Approach C: Deny + optional immediate close
  Summary: Future-only deny (Approach A) plus an "also close it now" follow-up in
   the confirm dialog that chains the existing stop/sell paths.
  Effort: M
  Risk: High (contradicts the agreed future-only spec; introduces a two-action
   mutation)
  Pros: Most complete escape hatch.
  Cons: User rejected this in D2; the "run as normal" intent is the whole point.
  Reuses: A + existing sell/stop.

## Recommended Approach

**Approach B, tightened.** The feature is "one click that lands on the right
list," and most of it already exists. But `Config.set()`
(`backend/service/config.py:448`) does a full `update_or_create` — a whole-value
replace with no append and no lock. `AGENTS.md` states multiple dashboard
clients are a normal deployment, so a frontend read-modify-write of the full
list can clobber another client's concurrent append (a lost-update window). The
append must therefore be **server-side**: a small dedicated endpoint reads the
current `pair_denylist`, de-dups the base token, and writes it back atomically
under a config-mutation lock. Hot-reload into running plugins is free
(`service/signal.py:52` subscribes and reloads). The badge reflects desired
state from the snapshot store so it is correct even before the reload lands.

This is the right call because atomic append is a correctness requirement under
multi-client use, not a rare edge case.

## Decisions (settled in this session)

- D1 — Surface: new entry inside the row "more …" overflow menu (`NDropdown` in
  `useOpenTradeColumns.ts`), reusing `useOpenTradeActions.ts`. Not a top-level
  button.
- D2 — Semantics: future-only. Append to `pair_denylist`; the open trade keeps
  running to its natural end. No immediate close.
- D3 — Reversibility: config-only undo. Deny is one-way from the UI; removal is
  editing the `pair_denylist` field. No symmetric "resume" action.
- D4 — Scope: append to `pair_denylist` plus a non-blocking badge on the row. No
  `symbol_list` cleanup (the denylist gate is already authoritative).
- D5 (post-review) — Append is server-side and atomic, because `config.set()` is
  a full replace and multiple clients are a normal deployment. The frontend
  sends the base token; the server de-dups and writes the new list.
- Branch note: this is a *new feature*, not part of the
  `refactor/remove-sidestep-mode` refactor; it is tagged on that branch by
  association, not intent.

## Open Questions

- De-dup / normalization location: the appended value is the **base token only**
  (e.g. `FO0`, not `FO0/USDT`), because `pair_denylist` is parsed
  `token_only=True` at `signal_runtime.py:340` and the deny gate compares the
  base token (`sym_signals.py:222`, `websocket_signal.py:570`). The server-side
  append de-dups on the base token; the frontend sends just the token.
- Idempotency UX: clicking "deny" when the symbol is already on the denylist is
  a no-op with a subtle "already denylisted" message. For an *already-denylisted*
  open trade, the menu entry stays **visible and enabled** but reads "Deny
  (already applied)" and the badge is shown, so it cannot look broken.
- Badge label default: "Denylisted - future entries blocked" (matches the
  `automation_paused` `NTag` style in `useOpenTradeColumns.ts:212`); a design
   pass confirms color/label.

## Success Criteria

- Clicking the new menu entry on a `FO0` open-trade row results in `FO0` being
  present in `pair_denylist` after the save, with no duplicate entries.
- The open `FO0` trade continues running its DCA/TP/SO logic unchanged.
- After the reload, a new `FO0` signal is blocked (verifiable via the
  `is_on_deny_list` gate in the active plugin).
- A badge on the row reflects the denylisted state.
- Regression tests cover: append de-dups, no close of open trade, deny-blocks-
  future-entry, and the UI menu entry + badge exist.

## Distribution Plan

Existing pipeline. Frontend (Vue/Vite) builds to `backend/static/`; backend
serves it. No new distribution surface.

## Dependencies / Blockers

- None. Hot-reload into running plugins is the only prerequisite and is already
  implemented (`service/signal.py:52` + `_reload_plugin`).

## Next Steps

1. Backend: add a small server-side append (a `Config` append under a
  config-mutation lock, or a `POST /orders/deny/{symbol}` that reads, de-dups the
  base token, and writes the full list back) — **not** a frontend
  read-modify-write, because `config.set()` replaces the whole value
  (`config.py:448`).
2. Frontend: add `handleDealDeny` to `useOpenTradeActions.ts` (clone
    `handleDealStop`), send the **base token only**, and wire it into
    `OpenTrades.vue` and the `NDropdown` `overflowOptions`/`onSelect` in
    `useOpenTradeColumns.ts`.
3. Frontend: add a "Denylisted" tag to `renderSymbolCell` driven by the
    `pair_denylist` snapshot; show the entry as "Deny (already applied)" when the
    symbol is already present.
4. Tests: server-side append de-dups and is idempotent; no close of open trade;
    "deny blocks future entry"; frontend menu-entry + badge presence; and a
    multi-client concurrent-append case (no lost update).
5. DESIGN.md pass for the badge label/color.

## What I noticed about how you think

## GSTACK REVIEW REPORT (plan-eng-review)

Target: this design doc. Verdict: APPROVE-WITH-CHANGES; 2 blocking issues, both
about write serialization, not about the happy path.

### Confirmed (evidence)
- Hot-reload into running plugins: `service/signal.py:52` subscribes to config
   changes; `_reload_plugin` (`:222`) re-runs `_prepare_runtime_settings`
    (`sym_signals.py:247`), refreshing `self._pair_denylist`. Premise 5 holds.
- Atomic mutation precedent: `service/lifecycle_mutation.py` provides a
   coordinator, but it is **per-trade-symbol** (`_locks: dict[str, Lock]`,
    `_lock_for(symbol)`), used by `trading_controls.py:226` and `orders.py:648`.
   A denylist append mutates *global* config, not one trade's lifecycle, so the
   per-symbol coordinator is the wrong primitive. Use a **global**
   `asyncio.Lock` on `Config` (the singleton at `config.py:211` already has one
   for instance creation; add a distinct write lock).
- Dedup precedent: `signal_runtime.py:385` `_dedupe_candidate_symbols` is a
   ready pattern to model the append de-dup on.
- Entry format: `pair_denylist` is a CSV `str`; runtime parse is token-only
    (`signal_runtime.py:340`). Append the **base token**, and serialize back to a
   single `str` via the same path `configSubmitPayload.ts:341` uses.

### Blocking issue 1 — no write serialization today (MUST FIX)
`Config.set()` / `batch_set()` (`config.py:448`, `:485`) do `update_or_create`
with no global lock. A frontend read-modify-write (Approach B as initially
drafted) loses updates under multiple concurrent clients, which AGENTS.md calls
a normal deployment. The approved D1 is a server-side append endpoint that holds
a `Config`-level write lock across read-current + serialize + `set()`. This is
load-bearing; without it, two clients can clobber each other's denylists.

### Blocking issue 2 — config-form save collides with the append (NEW, not in
design)
The full config form still saves `pair_denylist` as a whole via
`PUT /config/single` / `/config/multiple` (`config.py:563`, `:602`), a plain
full replace. If a client has the form open and saves while another client
appends via the new endpoint, the form **overwrites** the append. The
read-modify-write collision moves from the frontend into the form-vs-endpoint
race. Two acceptable resolutions:
  (a) Accept the residual form-vs-endpoint race and document it; the append
   endpoint is the only path that mutates at runtime, and the form is edited
   deliberately by a human.
  (b) Route the form's `pair_denylist` write through the same locked append
   (treat a full-list save as "append the delta vs. current, de-duped") so no
   save path can clobber a concurrent append.
Recommendation: (b) for a trading system where a silently-dropped deny means a
blocked symbol starts trading again. Cheaper than it sounds: one locked helper.

### Non-blocking
- Badge label/color still a DESIGN.md pass item (fine).
- Tests: add the multi-client concurrent-append case (D4) alongside deny-blocks-
  future-entry; it is the regression that proves issue 1 fixed.

### Scope
PASS. No creep. Approaches B/C documented and rejected; symbol_list cleanup and
symmetric resume out of scope.

### Resolution (settled in this review)
- D1: Server-side append endpoint. A `POST /config/denylist/deny` (shape
  TBD, base-token payload) reads current `pair_denylist`, appends the base
  token, de-dups (model on `signal_runtime.py:385`), serializes to a single
  `str`, and writes it under a new **global** `Config` write lock (not the
  per-symbol coordinator). No frontend read-modify-write.
- D2: Route the config form's `pair_denylist` save through the same locked
  append helper (full-list save = "append the delta vs. current, de-duped").
  No save path can clobber a concurrent append.
- Frontend: `handleDealDeny` cloning `handleDealStop`, sends only the base
  token; more-menu entry in `useOpenTradeColumns.ts`: `NDropdown`
   `overflowOptions` + `onSelect`; "Denylisted" badge in `renderSymbolCell`
   driven by the `pair_denylist` snapshot, showing "Deny (already applied)"
   when present.
- Tests: deny-blocks-future-entry, deny-does-not-close-open-trade, and the
   multi-client concurrent-append regression (proves D1/D2 fix the clobber).
