# Design: Accumulation-mode hardware-wallet custody (off-exchange recognition)

Generated by /office-hours on 2026-10-30
Branch: feature/background-recovery-watcher
Repo: TBMoonwalker/moonwalker
Status: APPROVED 2026-10-30 (independent 3-round spec review converged PASS, 8/10)
Mode: Builder (full rigor — real money)

## Problem Statement

When operating Moonwalker in **accumulation mode**, an operator may move some or all
of an accumulated base asset off the exchange into a hardware wallet (Ledger, etc.)
for cold storage, and later move coins back onto the exchange. Moonwalker must:

1. **Recognize** that coins have left the exchange to a wallet, and **recognize** when
   they return — without the operator having to tell it.
2. **Keep the position working as if the coins were still on the exchange** — the
   recorded position, average cost, valuation and uPNL are unchanged by the move.
3. **Handle the sell leg safely**: while coins are off the exchange they cannot be
   sold by the bot (the coins are not there). The operator's choice is that **no exit
   fires while any coin of that base asset is off-exchange** — the move is blocked,
   not stranded.
4. **Never initiate the move itself.** The move is performed by the operator on the
   exchange side (a withdrawal to the wallet, a deposit back). Moonwalker only
   *observes* the move.

This is accumulation-only. DCA and other modes are out of scope.

## What Makes This Cool

The position the operator "owns" is not the same thing as "what sits on the
exchange." Today Moonwalker conflates them through the live balance; this design
gives accumulation a first-class **custody dimension**: a per-base-asset record of
"coins the operator holds but that are currently not on the exchange." It lets the
bot HODL in cold storage while it keeps accumulating a live on-exchange tranche, and
it makes the "sell while part of your stack is in a wallet" case a *deliberate,
audited decision* instead of a silent data race — which, with real money, is a
safety story as much as a feature.

The "cool" technical bit: a withdrawal/transfer **event** from the exchange's own
history is a *positive, unambiguous* signal that a coin moved to a wallet. It kills
the entire "was this a sale or a wallet move?" ambiguity that a balance-difference
approach cannot escape.

## Constraints

- **Single-node, single-instance**, multi-client (desktop/mobile/tabs). No cross-
  instance coordination. Custody state is one row in the instance's own database.
- **Detection is observation only.** Moonwalker reads move history and balance; it
  must never call `withdraw`, `transfer`, or any capital-mutating method. The
  exchange API key is expected to hold **no** withdrawal permission, and the custody
  code path must be constructed so it cannot invoke mutation even if a key were
  over-scoped.
- **Real money.** A blocked/stranded exit is the worst failure mode. The safety
  posture is: never let a weak signal silently block a genuine sell; never let a sell
  move coins that are not on the exchange; never let a stale or reversed ledger entry
  strand the sell leg.
- **Reuses, not reinvents.** There is already a dedicated accumulation decision
  service owning execution, capital enforcement, persistence, recovery, a durable
  lifecycle-operation audit table, a `lifecycle_mutation_coordinator`, a
  `run_sqlite_write_with_retry` write seam, a per-symbol/account `account_scope`
  binding, a "shared base-asset ownership is ambiguous" guard, a dust-archive path,
  and a balance-change pub/sub notification. Custody rides all of it.
- **Exchange-agnostic but capability-gated.** Target venues are Binance, Bybit,
  Bybit EU via `ccxt.async_support`. The feature is enabled only where the venue
  exposes official move history; it is **disabled** (never heuristic-fallback) on a
  venue that does not.
- **No `edit` tool** for Python in this repo; files go through the `write` tool then
  Ruff. This affects *how* the change lands, not the design.

## Premises

1. **Valuation, average cost and uPNL already survive the move for free.** The
   accumulation position is recorded by Moonwalker from *its own exchange fills*
   (`holding.accumulation_net_quantity`, `accumulation_remaining_cost`,
   `accumulation_contributed_quote` on the `OpenTrades` holding), and
   `AccumulationReturnTotals.last_quantity`/`Last_cost` drive valuation
   (`performance.py`). None of these read the live exchange balance. So
   "keep working as if the coins are still there" is already the true state of the
   read-only numbers; the work is (a) detecting the move and (b) gating the **sell**
   leg so it cannot deliver coins that are not on the exchange. **This must be
   verified before build, not assumed.**
2. **Accumulation has no automatic close.** Sells are operator-initiated
   (`close`, `retry_close`, `sell_partial` in `sales.py`). So "block exits while
   coins are away" is purely a gate on the operator's own command, never on an
   automated risk control.
3. **Custody is a per-base-asset fact.** A wallet withdrawal reports the *base*
   asset and an amount, not the trading pair. A base asset should map to one
   accumulation symbol; the existing "shared base-asset ownership is ambiguous" guard
   (in `ownership_declaration.py` / `account_rebind.py`) already enforces that, so the
   custody ledger keys on the base asset and rejects the ambiguous case.
4. **The move is operator-driven and may not be "clean."** The operator may sweep
   part or all, may do it in multiple moves, and **fees on the deposit side can make
   the returned amount smaller than the withdrawn amount** (the operator's explicit
   D7 caveat). A "fully returned" check must therefore tolerate a dust epsilon, or a
   hair of fee-dust would hang the latch forever.
5. **The strategy may keep accumulating into the on-exchange tranche while coins are
   cold** (operator's choice). New buys add fresh on-exchange coins and do **not**
   change the off-exchange ledger; the latch condition is on the off-exchange
   remainder, so it is unaffected by new accumulation.
6. **Detection must be incremental and idempotent.** Exchange move history is often
   windowed (~1 month on some venues), so the detector polls forward from a
   persisted cursor (last-seen `since`/transaction id) and dedupes by
   transaction/withdrawal id, never re-deriving from a full history window.
7. **Moves are not final until the venue confirms finality, and that can reverse, within
   the venue's queryable window.** A move that has been counted as completed can later be
   cancelled, fail, or be reversed (a chain reorg, a cancelled or mis-stated
   withdrawal). The detector must therefore re-check the status of every previously-counted
   move that is still within the venue's queryable history window, not just read new ones,
   and be able to *revert* a ledger contribution. Once a move ages out of that window,
   re-checking is no longer possible, so the detector trusts the persisted `final` flag and
   the balance cross-check acts as the backstop for any reversal the window no longer
   surfaces (R2-1).

## Approaches Considered

### Approach A: Pure balance reconciliation (recorded − on-exchange free)

Compute off-exchange = `max(0, recorded_net_quantity − on_exchange_base)`.

- ✅ No new API surface; works on every venue.
- ✅ Simple to implement.
- ❌ **Falsifies against real money:** a balance drop is ambiguous — it could be a
  sale the operator made on the exchange UI, a transfer to a sub-account, or an order
  locking funds, not a wallet move. One misread can latch a *legitimate* sell or,
  conversely, miss a real move.
- ❌ Cannot tell "left to a wallet" from "sold on the exchange," so it cannot
  distinguish a custody event from a position-reducing trade.
- Ruled out as the *primary* detector (D6/D8). Kept only as a cheap cross-check
  against the authoritative event signal, never as the latch trigger.

### Approach B: Official move history (CHOSEN)

Poll the exchange's own move history via `ccxt` — `fetch_ledger` where available
(Bybit), else `fetch_withdrawals` + `fetch_deposits`, else `fetch_transfers` — each
behind a capability check, **read-only**, polled incrementally from a persisted
cursor and deduped by transaction id. A completed *withdrawal* of the base asset
increments off-exchange for that base; a completed *deposit* decrements it. The
detector also **re-checks the status of every previously-counted move** and reverts
on a later failure/reversal. Balance is a cross-check, not the trigger.

- ✅ A withdrawal/transfer event is a **positive, unambiguous** "coins moved to a
  wallet / coins came back" signal. Kills the sell-vs-wallet-move confusion.
- ✅ No new capital-mutating API; the code path needs no withdrawal permission
  (and is constructed so it cannot call one regardless of key scope).
- ✅ Reuses the exchange client, the lifecycle-mutation coordinator, the durable
  `AccumulationLifecycleOperation` audit table, the dust-archive path, and the
  balance-change notification.
- ✅ Idempotent and self-correcting: re-checks prior moves and reverts on reversal.
- ❌ Capability-gated: some venue classes expose deposits only, or nothing
  (Bybit EU may differ from Bybit). **Decision (operator, D8):** disable the feature
  on a venue that lacks the capability rather than fall back to the weak heuristic.
- ❌ A move can be *pending/processing/failed/reversed*; only **final** moves count,
  and detection must debounce and re-check so a transient, failed or reversed move
  never opens or strands the latch.
- ❌ "Prove the key is read-only" is **not** generally verifiable through CCXT
  (`exchange.has` maps method availability, not key scope); the guarantee is enforced
  by *construction* (see Approach B safety note and Open Questions), which is weaker
  than a runtime check and is accepted as a deliberate trade-off.

### Approach C: Operator-declared amount

The operator records "I moved N base to my wallet"; Moonwalker tracks the expected
off-exchange and reconciles the balance against it (a near-relative of the existing
`declare_ownership` / `rebind_account` commands in `ownership_declaration.py`).

- ✅ Zero false positives; the operator is the source of truth.
- ❌ Adds a manual step per move — directly against the operator's "It only has to
  recognize the moves" requirement.
- Ruled out (D3 auto-detect). Reused *structurally* (the command/commit/`from_operation`
  shape), not as the trigger.

## Recommended Approach

**Approach B, with a balance cross-check, a per-base-asset custody ledger, a LATCH on
the sell leg, and a dust-tolerant, self-correcting "returned" gate.** Concretely:

1. **New read-only seam on the exchange client** (`backend/service/exchange.py` +
   `ccxt.async_support`): `fetch_account_movements(base_asset, since_ms, …)` that
   prefers `fetch_ledger`, then `fetch_withdrawals`/`fetch_deposits`, then
   `fetch_transfers`, each guarded by `exchange.has[...]`; returns a normalized
   `direction ∈ {out (withdrawal), in (deposit), internal (transfer), …}`, amount,
   status, txid/withdrawal id and `created_at`. **No capital-mutating method is
   ever referenced by the custody path.**
2. **Read-only invariant by construction + attestation (not runtime key-scope proof).**
   CCXT exposes no generic key-scope introspection (`exchange.has` is method
   availability, not permission), and per-venue scope endpoints are inconsistent and
   may be impossible. The guarantee is enforced two ways: (a) the custody code path is
   *provably* read-only by a test that asserts it imports and calls **only** read
   methods — no `withdraw`, `transfer`, or mutation of any kind — plus a capability
   probe that enables the feature *per venue* on the presence of
   `fetch_ledger`/`fetch_withdrawals`/`fetch_deposits`; and (b) the operator is
   attested, at enable time, that the configured exchange API key carries no
   withdrawal permission. The design does **not** claim a runtime proof that a key is
   unscoped; it claims "the bot cannot move your coins" by construction plus the
   operator's attestation. Whether any target venue can additionally prove key scope is
   an Open Question (R1-1), not a build blocker.
3. **Detector module `backend/service/accumulation/custody.py`** and a **new model
   `AccumulationCustody`** (in `model/accumulation.py`): one row per base
   asset/activation — `off_exchange_base`, an append-only ledger of
   `{txid/withdrawal_id, direction, amount, status, observed_at_ms, final}` for the
   audit trail, a `last_seen_cursor`, and a **presentation-only** `state`
   (`none | active | returning | dust_pending`; see R1-5 — the latch keys off the
   threshold in step 5, *not* off `state`). Mirrors the existing
   `AccumulationReturnTotals` "derived, atomically updated" table.
4. **Incremental, debounced, self-correcting detector.** A low-frequency
   (e.g. 60–120 s) poll driven off the existing balance-change pub/sub
   (`accumulation_input_notifications`) plus its own cadence. On a **final**
   `out`/withdrawal event it increments `off_exchange_base` for the base; on a final
   `in`/deposit it decrements. `internal`/sub-account moves are recorded but do
   **not** latch (they remain on the exchange). The detector **re-checks the status of
   every previously-counted move still within the venue's queryable history window each
   run** and **reverts** the ledger contribution
   of any move that transitions to failed/cancelled/reversed (the R1-2 correction
   path), re-releasing the latch if the revert brings `off_exchange_base` back to
   `<= dust_tolerance`. Every flip goes through
   `lifecycle_mutation_coordinator.mutation(symbol)` + `run_sqlite_write_with_retry`
   and writes an `AccumulationLifecycleOperation` with `action="custody_move"` for the
   durable audit trail. A move must reach a final status and be **stable across a
   confirmation window** (debounce) before it may open/flip the latch, so a pending,
   failed, reversed, or in-flight move never does.
   A move counts toward `off_exchange_base` only while **final**; once it ages out of the
   venue's queryable history window (~month on some venues) the detector can no longer
   re-fetch its status, so it **trusts the persisted ledger `final` flag** from then on (a
   final move is, by construction, past the operator's own on-chain finality, so a
   post-finality reversal is not a live risk on the operator's chosen chains). The boundary
   is stated, not hidden: reversals *beyond* the queryable window are **out of scope for
   automated reversion**, and the **balance cross-check is the standing backstop**. A
   counted off-exchange total that no longer matches the venue balance (a reversal the
   window no longer surfaces, or an operator deposit made on the UI) is surfaced to the
   operator through the existing cross-check alerting instead of silently stranding the
   sell leg; a regression test asserts a reverted-while-aged-out move never leaves the
   latch held silently (R2-1).
5. **LATCH on the sell leg** (operator's D2/D4/D5/D7 choice), as the **single
   chokepoint**: a custody check is added at `sales.py._claim_sale`, which is the one
   path all three operator exit commands funnel through — `close`, `retry_close` and
   `sell_partial`. The build must **verify this chokepoint by test** (R1-3): assert
   that none of the three can authorize a sale while `off_exchange_base > 
   dust_tolerance`. When blocked, the close is rejected with a clear reason
   (`OFF_EXCHANGE_CUSTODY_ACTIVE`) and, per the operator's D9 choice, **dropped, not
   auto-resumed** — no placement is created and the operator re-issues after the
   coins return. New accumulation **buys keep firing** into the on-exchange tranche
   (D5) and do not touch the latch.
6. **Dust-tolerant, self-correcting "returned" gate** (the D7 caveat + R1-4 + R1-2):**
   custody is *cleared* when `off_exchange_base <= dust_tolerance`. Two distinct
   residual types are handled: (a) an **on-exchange** accumulation remainder keeps
   riding the existing **dust-archive path** (`dust.py:archive_accumulation_dust`);
   (b) a permanent **off-exchange fee residual** (a deposit that lands shorter than the
   withdrawn amount by the fee) is handled by a **dedicated custody-clearing rule**:
   when off-exchange is reconciled to within `dust_tolerance`, the residual is **retained**
   in the append-only ledger as a `custody_move` clearing record (base txid + residual
   amount, for the audit trail) while the running total is **reset to `0`**, so that total
   cannot re-latch a subsequent move while `state` reads clear. The residual is not
   discarded; it is the cleared event, and only the running `off_exchange_base` total is
   zeroed (R2-2). `dust_tolerance` is a config
   key, proposed default `max(<exchange min-tx/withdrawal fee for the base>, <tiny
   epsilon>)`.
7. **Operator visibility + notification.** While active, the per-symbol status
   surface shows "X base in wallet, detected since …, last move <txid>"; close
   controls surface the lock + reason. Detect/clear each emit a notification through
   the existing Telegram monitoring path.
8. **Return detection** = a final `in`/deposit event driving `off_exchange_base` back
   through `<= dust_tolerance`, after which the latch releases and the (re-issued)
   close can proceed.

9. **Capability re-evaluation.** Because exchange selection is a hot-reloaded config
   (R1-8), the detector **re-evaluates the capability gate on each run and on any
   venue change**, not only at startup. A runtime switch to a capability-less venue
   (e.g. Bybit EU) immediately disables detection for that venue; a stale enable
   decision is never applied.

**Why B over A/C:** the operator explicitly wants recognition without a manual step
(removing C) and will not accept a weak signal latching a real money move (removing
A as primary). B delivers both: an unambiguous, audited, read-only-by-construction,
self-correcting signal with a safe degrade (disable, re-probed) instead of a
dangerous fallback.

## Open Questions

- **Key-scope proof mechanism (R1-1).** CCXT has no generic key-scope introspection
  and per-venue scope endpoints are inconsistent; the read-only guarantee is by
  **construction + attestation**. Decide: do any target venues (Binance/Bybit/Bybit
  EU) expose a permissions/scope endpoint worth a best-effort *confirm* probe, and is
  attestation acceptable, or is the by-construction test sufficient on its own?
- **Bybit EU capability.** Confirm whether the `bybiteu` CCXT class exposes
  `fetch_ledger`/`fetch_withdrawals`/`fetch_deposits`. If not, the feature is
  **disabled on Bybit EU** by design (D8) — verify and document, do not hack around
  it.
- **`dust_tolerance` default.** Needs a sensible, exchange-aware default (min
  withdrawal fee or a fixed epsilon per base) — confirm the value, or make it a
  per-activation config.
- **Move finality / debounce window, and the aged-out edge.** Confirm the
  debounce/correction window versus the slowest expected on-chain confirmation the
  operator uses (BTC confirmations vs an instant EVM chain differ wildly by orders of
  magnitude); too short and a reversing move can momentarily strand or re-open the latch.
  This also fixes how long the detector *re-checks* each still-in-window move, and the
  explicit out-of-scope boundary for reversals beyond the venue's queryable history
  window, where the balance cross-check is the standing backstop (R2-1).
- **`internal` transfers to a sub-account.** Recorded as "still on the exchange," not
  as custody. Confirm the operator's sub-account transfers are not a "moved to
  wallet" intent; if a sub-account should ever *count* as off-exchange, make it an
  explicit config flag, not the default.
- **Cross-check alerting.** When the balance cross-check disagrees with the event
  ledger (e.g. a sale the operator made on the exchange UI, not through the bot),
  decide *notify + reconcile* vs *ignore* — but the *ignore* branch may only cover
  on-exchange events the operator can act on themselves (such as a UI sale); it can
  **never** apply to a venue-undetectable aged-out reversal, which is always surfaced
  for reconcile so the stranded-sell worst case cannot reopen (R3-1). The aged-out
  regression test therefore asserts the latch is not held silently even when the
  cross-check would otherwise have the operator ignore the mismatch.
- **`sell_partial` strictness (reserved for v1).** Per D2/D4/D7 the operator rejected
  a per-lot split, so the **committed v1 default is to block ALL exits, including
  partials, while any coin is off-exchange.** A partial sell of *only the on-exchange
  portion* is noted as a future option and is out of scope for v1 (R1-7).

## Success Criteria

- A final withdrawal of N base to a wallet is detected within one confirmation window;
  the custody row and a `custody_move` audit operation are written; the operator is
  notified.
- While `off_exchange_base > dust_tolerance`, **no** close, retry_close or
  sell_partial on that base asset is authorized — verified by a test that none of the
  three entry points can authorize a sale while blocked (R1-3). The operator's close
  attempt is rejected with `OFF_EXCHANGE_CUSTODY_ACTIVE` and **no** placement is
  created (D9: dropped, not auto-resumed).
- Valuation, average cost and uPNL are **unchanged** by the move (verified with a
  before/after test against `AccumulationReturnTotals`).
- A final deposit returning the base through `dust_tolerance` clears custody (resets
  `off_exchange_base` to 0, R1-4), releases the latch, and lets a re-issued close
  succeed; a fee-short deposit leaves a residual handled by the dedicated off-exchange
  clearing rule without re-latching.
- On a capability-less venue, the feature is **off** (re-probed each run / on venue
  change, R1-8); no detection, no latch, no false blocking.
- A move that is `pending`/`failed`, an `internal` sub-account transfer, or a
  previously-counted move that later reverses/fails does **not** open, strand, or
  keep the latch — the detector re-checks and reverts (R1-2), with a regression test.
- A move that reverses *after* it ages out of the venue's queryable history window does not
  silently strand the sell leg: the detector trusts the persisted `final` flag and the
  balance cross-check backstop surfaces it for reconcile rather than holding the latch
  (R2-1), with a regression test.
- The custody code path is provably read-only by construction (a test asserts no
  capital-mutating method is reachable from it); the operator attestation is recorded.
- All existing accumulation, sales, dust and account-rebind tests still pass.

## What I noticed about how you think

- You reached for the *exchange's own ground truth* before trusting your own balance
  math. "Research the ccxt api if there is a way to see a 'withdraw'" is a
  first-principles instinct — most people would have written a balance-difference
  heuristic and called it a day. That one question converted the hardest part of this
  feature (the sell-vs-move ambiguity) from "impossible" to "look at their log."
- You keep the operator in the driver's seat *by construction*. "Moonwalker must not
  initiate the coin move," "disable on a venue that can't prove history, don't fall
  back to guessing," and "drop the blocked close, I'll re-issue" are all the same
  principle: the bot observes and proposes, the operator commits. Consistent and
  money-appropriate.
- Your fee caveat on D7 ("fees can reduce the base amount and can still be
  completely transferred") is exactly the kind of edge case that ships a latch that
  never releases. Naming it up front is the difference between a feature that works
  in the demo and one that works at 3 a.m.
- You accepted the strongest safety posture on the *dangerous* axis — no auto-close,
  a full latch while coins are away, disable-not-fallback — while keeping the
  *convenient* axis loose (recognition is automatic). That's a good risk split.

### R3-1 — clarity (minor)

**Problem**

> The aged-out resolution (Premise 7, the new Step 4 paragraph, and the new Success Criterion) makes the balance cross-check 'the standing backstop' for the stranded-sell worst case, but the strength of that backstop is fully contingent on the still-open 'Cross-check alerting' question, which explicitly leaves 'notify + reconcile vs ignore' undecided. If that question resolves to 'ignore,' a move that reverses while aged-out leaves a phantom off_exchange_base, the latch still holds, and the documented worst case ('never let a stale or reversed ledger entry strand the sell leg') is re-opened for the aged-out case even though the in-window case is truly closed. That dependency of the aged-out guarantee on the unresolved cross-check branch is not stated, and a regression test phrased 'does not silently strand' would pass as long as it exercises only the surface path and never the ignore path for an aged-out reversal.

**Remedy**

> State explicitly that a mismatched aged-out reversal must always be surfaced for reconcile, or scope the 'ignore' branch of the 'Cross-check alerting' question to operator UI sales so it cannot apply to a venue-undetectable aged-out reversal; extend the regression test to assert the latch is not held silently when the cross-check would otherwise be ignored for an aged-out reversal.
