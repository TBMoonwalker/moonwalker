# Design: Remove Sidestep Mode Completely

## Problem Statement

Sidestep mode (`trade_mode = "sidestep"`) is a spot-only multi-leg campaign
system: a DCA leg can sell a "bearish" leg, hold the position in a waiting
state across legs, and re-enter later. It is woven through a dedicated DB model
(`SpotCampaigns`), a runtime service (`SpotSidestepCampaignService`), 7 config
keys, the DCA engine, the trade-lifecycle layer, capital budget, controllers,
and a "Waiting Campaigns" UI. The goal is to remove it completely so
`dynamic_dca` is the sole trade mode, without disturbing any other
functionality.

This is an existing, shipping open-source trading bot. The hard part is not the
deletion; it is deleting the sidestep branches while leaving the `dynamic_dca`
path byte-for-byte correct, and deciding what happens to existing data and
schema. Those data/schema calls are one-way, so they are explicit
recommendations below rather than silent choices.

## Approaches Considered

### Approach A: Surgical branch removal, keep schema (RECOMMENDED)
Delete all sidestep code paths and the `dynamic_dca`-only guards, but leave the
DB schema and existing rows untouched: keep the now-unused
`campaign_id`/`lifecycle_mode`/`exposure_state`/`waiting_*`/`reserved_reentry_
quote` columns on the shared trade tables and the `spotcampaigns` table on
disk. Only remove the `SpotCampaigns` *model + registration* so it stops being
written.

- Effort: M.  Risk: Low.
- Pros: zero risk to existing databases/backups; `generate_schemas` + additive
  column migration still run clean; an old DB just keeps dormant columns; the
  diff is the smallest that fully kills the feature; trivially reversible via
  git.
- Cons: leaves dead columns in the schema and a dormant table; the
  "complete removal" is code-complete, not schema-complete.
- Reuses: the existing `dynamic_dca` branches, the existing additive-migration
  machinery (no new migration, just stop emitting the dropped entries).

### Approach B: Full removal including schema drop
Same as A, plus drop the `spotcampaigns` table and the
`campaign_id`/`lifecycle_mode`/`exposure_state`/`waiting_*`/
`reserved_reentry_quote` columns from the shared trade tables via a migration.

- Effort: L.  Risk: High.
- Pros: truly complete, nothing dormant.
- Cons: SQLite `DROP TABLE`/`DROP COLUMN` on a live trading DB is a one-way
  door; breaks restore of any pre-removal backup; `OpenTrades`/`Trades`/
  `ClosedTrades`/`TradeExecutions`/`PlacementIntent` carry these columns
  shared with `dynamic_dca`, so dropping them means rebuilding the table (not
  `ALTER DROP` on older SQLite) or a careful column-by-column migration — high
  chance of corrupting in-flight trades. Over-engineered for a feature the
  operator can simply not enable.
- Reuses: needs new migration logic that has no existing pattern.

### Approach C: Defer, hard-disable only
Keep all code, force `trade_mode = dynamic_dca`, hide the UI. Minimal diff.

- Effort: S.  Risk: Low.
- Pros: smallest, safest.
- Cons: contradicts "remove completely"; leaves 60 files of dead code; the
  dormant service still loads and subscribes to config. Not what was asked.
- Reuses: everything.

**RECOMMENDATION: Approach A.** It satisfies "remove completely without
disturbing the rest" — the feature is code-complete-dead and `dynamic_dca` is
untouched — while keeping the DB schema reversible. Schema drop (B) is the only
part I'd actually worry about, and it's the one-way door the user can decline.
Dormant columns are the standard, safe tradeoff for a feature deletion and
cost nothing at runtime.

## Data & Schema Decisions (one-way doors — explicit, your call)

These determine whether "complete" means "code" or "code + on-disk data."

**D1 — Existing `trade_mode = 'sidestep'` config rows / backups.** After
removal the canonical value space is `{dynamic_dca}`. A restore that reads a
pre-removal backup currently maps legacy keys to `sidestep`
(`config_migrations.py:resolve_legacy_trade_mode`).
- A (recommended): Treat any legacy `sidestep`/`sidestep_campaign_enabled`/
  `trade_lifecycle_mode=sidestep_reentry` row as `dynamic_dca` on the next
  migration (drop the sidestep mapping branch). No data is lost; it just stops
  meaning "sidestep." Effort S, risk Low.
- B: Reject/erase such rows with a loud warning. Effort S, risk Med (can block
  an operator's restore).
- Recommendation: **A** — a dead feature's saved setting shouldn't gate a
  restore; collapsing to `dynamic_dca` is the least-surprising outcome.

**D2 — On-disk DB schema (the shared trade-table columns + `spotcampaigns`).**
- A (recommended, = Approach A): leave the columns and the table on disk; only
  stop reading/writing them and unregister the model. Effort S, risk Low,
  reversible.
- B (Approach B): drop the table and the sidestep-only columns. Effort L,
  risk High (one-way; risks in-flight trades / old backups).
- Recommendation: **A** for this PR. If you later want schema drop, it's a
  separate, well-tested migration.

**D3 — Durable `ConfigMigration`/backup rows already written.** Keep the
`TRADE_MODE_MIGRATION_VERSION` migration idempotent; it just stops producing a
`sidestep` value. No new migration required. (Follows from D1=A, D2=A.)
